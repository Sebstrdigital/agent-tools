# Parallel planning and attempt workbooks

Use this guide only when parallel work is likely to repay its isolation and integration costs. It is a manual coordination aid over the existing execution service, not a scheduler, snapshotter, lock manager or authorization mechanism. The current service permits multiple pinned, inspection-only reviewers in the same clean Git worktree root when their recorded candidate revision matches. All other workers retain exclusive workspace ownership, including while paused or waiting; dirty, unverifiable and legacy reviewer runs remain exclusive. This is a best-effort change detector, not an immutable snapshot or filesystem lock. Do not create worktrees, merge, copy private material or delete anything without the applicable authority. Never widen a reviewer's fixed inspection-only grant.

## Plan before dispatch

1. Capture the task outcome, candidate and boundaries, and decide whether serial work is cheaper. List slices with their acceptance/checks, dependencies, intended write surfaces, shared resources and integration order. Independent behavior is not enough: overlapping writes, shared mutable test resources and hidden dependencies also prevent safe concurrency. Reject missing dependencies and cycles; schedule a slice only after its dependencies and their evidence are valid for its input candidate. A contract can enable independence only when both sides actually agree on it.
2. Identify the exact starting revision **and** dirty tracked and untracked content relevant to the task, including deletions, modes and symlinks. A commit ID alone does not identify a dirty candidate. Inspect ownership before touching existing changes. Do not silently copy untracked/ignored files, credentials or other private material to a worktree; identify and obtain authority for necessary content first. If a complete, authorized and verifiable baseline cannot be established, serialize in the existing workspace instead of pretending a fresh checkout is equivalent.
3. Assign separate authorized, existing linked worktrees to concurrent builders, with the intended baseline verified in each. Account separately for ports, databases, directories, accounts and other shared external resources. A different cwd alone does not isolate those resources. Never run parallel writers in one workspace. Do not create worktrees implicitly; the service only admits the current checkout or an existing linked worktree.
4. Prepare one compact attempt workbook per worker/run in the task's project-local workspace, unless conversation or an existing record already carries equivalent information. Do not include secrets. Send the worker the relevant contract, identity and boundaries, not the entire archive. Workbooks are coordination records, not authenticated grants or a substitute for service-owned state.
5. Reconcile completed slices before integration: inspect exact changes, ownership and evidence, detect baseline or external mutations, and resolve conflicts under applicable authority. Do not overwrite unrelated work or blindly replay operations after interruption. Integrate in dependency order only if the operation is authorized. Any changed input invalidates affected downstream checks and reviews; rerun them against the new candidate. Final verification and independent review cover the complete integrated candidate, not merely individual slices.

## Clean-baseline route using the existing service

When all task-relevant work is already in an authorized clean revision, a cheaper path avoids dirty-state transfer: establish the exact revision and inspect tracked, untracked, ignored and external inputs separately; create three fresh, task-owned project-local linked worktrees at that revision under applicable authority; verify each actual worktree and assign one builder per worktree through the existing execution service. Give each builder distinct ports, directories, databases or other shared resources as applicable—the service enforces workspace ownership, not those other allocations. Do not assume Git's clean status covers ignored files or external dependencies. Ordinary Git and service workspace checks are not a sandbox against hostile parent swaps or unowned writers; use this route only when the actual environment and resources are independently isolated from them. Keep the worktrees and evidence; no implicit cleanup, commit, merge or install follows.

After builders stop, the service can admit two pinned read-only reviewers to the *same verified clean worktree and revision*. This does not solve integrated review of dirty builder outputs: reconcile and integrate under applicable authority, then use a separately verified review candidate; when that candidate is dirty, the shared-clean-review admission does not apply. The synthetic service test covers admission with three real linked worktrees and fake transport, not live provider execution or integrated acceptance.

For independent focused reviews, give each reviewer the same immutable candidate identity, scope, rules and relevant evidence, with complementary questions. For a clean worktree the service checks the revision, Git status, index flags and saved grant at admission, rearm or reply, and termination; it invalidates active review evidence when it detects a change. On service reconstruction it conservatively invalidates **all recovered active or paused shared-review evidence**, even if Git is clean, and blocks further operations pending reconciliation: changes or failed journal writes during absence cannot be ruled out. A missing workspace uses its retained admission identity to invalidate peers. Pause and stop remain available without a candidate check during normal operation. Dirty or unverifiable workspaces require serial review or separate authorized, verified workspaces. Git status does not detect ignored files, transient change-and-restore, all filesystem races, external dependencies or every stat-cache deception. A revision token is not proof of immutable content; account for external mutation independently. Reviewer sessions remain read-only and cannot execute mutation experiments or accept the work. Do not claim an independent review occurred if it did not.

## Explicit dirty-candidate observation

[`scripts/addy-candidate.mjs`](../../../scripts/addy-candidate.mjs) is an opt-in content observation—not a transfer or snapshot. The candidate and graph modules require Node.js with `import.meta.main` support; unsupported runtimes fail explicitly rather than silently skipping a CLI action. **Before inventory**, obtain actual authority to read local repository-control data and path names. The explicit `--authorize-repository-control` switch is a declaration, not authenticated consent. Inventory reads `.git/config` contents, walks local `.git` metadata, and invokes trusted Git to read HEAD, refs, index, tree objects and local object-store/pack bytes; pack reads can include bytes for objects outside the named candidate paths. It also enumerates worktree path names and directory metadata, including ignored untracked names. Without a coordination boundary it does not read worktree file contents or evaluate `.gitignore`, `.git/info/exclude` or external exclude files. With a boundary, inventory also reads the explicitly authorized coordination-artifact contents described below. Git, Node, OS libraries and the script itself are also read as executable resources. Do not run inventory unless those reads and name disclosure are authorized.

The aid supports a real local `.git` directory and a restrictive basic `[core]` configuration. A linked worktree is supported only when it is inside an explicitly named, real owning project root and the caller separately authorizes that owner's shared Git-control/object boundary. This additional scope includes the linked worktree's `.git` pointer, selected per-worktree `gitdir`/`commondir` pointers, common `.git/config`, refs, index/object storage and metadata walks over the common `.git`, including other worktree control-directory names and metadata. It checks the pointer, backlink and common directory against that owner and rejects escapes, symlinks, hard links and detected replacement. It rejects other config keys/sections (including includes, external excludes, helpers and filters), alternate/promisor object stores, and unsupported Git states. System/global Git config is disabled, inherited `GIT_*` settings are removed, filesystem monitor and lazy fetch are disabled, and no status, diff, checkout or hooks are invoked. This is a deliberately narrow compatibility boundary, not a general Git-config sanitizer or protection from hostile concurrent replacement. If the repository cannot meet it, stop rather than bypassing the checks.

### Optional opaque directory-prefix exclusions

When directory contents and their names are not authorized, explicitly declare each relative directory prefix **before inventory** using `--authorize-excluded-prefixes --exclude-prefix PREFIX` (repeat the latter). Initialize coordination first, without prefix options. The same declarations and authorization must be supplied on every inventory, capture and verification. Prefix authorization and overlap with all declared coordination and nested-worktree boundaries are validated before those boundaries are read. For prefixed CLI capture/verify, the selection file's absolute path must be printable ASCII, outside every excluded prefix and have no symlink components; unsupported selection paths are rejected before reading the file. The observer uses literal Git exclusion pathspecs to prune these directories before untracked enumeration; it does not list or read their descendants. It does inspect prefix/ancestor directory metadata and ancestor names, and repository-control and Git object-pack reads retain the separate authorization and limitations above. It rejects tracked HEAD or index overlap, symlink/non-directory components, spelling aliases, overlapping exclusions and overlap with coordination or declared worktree boundaries. The current implementation supports only Darwin with `git version 2.54.0 (Apple Git-157)`, at most 32 printable-ASCII prefixes of at most 512 characters, and printable-ASCII tracked paths when this mode is used; unsupported runtimes and paths fail rather than being assumed equivalent. This deliberately narrow Git/runtime gate reflects the synthetic pruning tests, not a general guarantee about every build bearing that version string. Unobserved prefixes may contain nested repositories: no claim is made about them. Unknown nested repositories outside the exclusions still fail closed.

Prefixed observations have `coverage: partial` and record `excludedPrefixes` in new v5/v6 coordination manifests (v7 without coordination); v2–v4 manifests remain unchanged. Comparison accepts matching v6 owner/v5 linked prefix lists with no individually excluded paths and explicitly returns **partial** scope: equality covers only the selected observed HEAD, index and worktree fields, not the excluded directories or the other manifest exclusions. For `addy-compare.mjs`, pass `--authorize-excluded-prefixes --exclude-prefix PREFIX` for the same scopes on both sides. Never infer excluded content is equal, absent, safe or unnecessary. No prefix is implicitly copied. This is ordinary drift detection under trusted local processes, not an OS sandbox or protection against hostile parent replacement. The macOS denied-read test and positive control cover synthetic cases on the tested Git/runtime, not all platforms or a complete syscall trace.

After reviewing the inventory, create a JSON object with `include` and `exclude` arrays that together name **exactly every inventoried path**, with no duplicates. Include a path only with authority to read its HEAD, staged and worktree contents; exclude sensitive or unapproved paths explicitly. The selection file itself is read as supplied by the caller. A new, omitted or extra path fails closed before any worktree file or selected blob is opened. Any explicit path exclusions produce `coverage: partial`; do not present that digest as complete. Store selection and output only in authorized project-local locations; they contain sensitive path names even though raw file contents are not copied.

For the normal project-local flow, separately authorize coordination-artifact reads with `--authorize-coordination-artifacts` and explicitly initialize a fresh `.agent-work/addy-coordination/TASK` boundary. This scope permits inventory, capture and verification to read the **contents** of its marker, selection, all retained manifests and graph events (and filesystem metadata), not merely their names. It is exclusively for the tool-owned marker, `selection.json`, generated `manifests/<digest>.json`, and the graph journal named `graph`—never put source, credentials, private data or unrelated work there. The switch is a declaration, not authenticated consent. Initialization refuses an existing boundary and tracked overlap; later observations reject tracked files, unknown names, malformed artifacts, symlinks and hard links there and check for boundary changes during capture. Each generated manifest retains the marker's random coordination ID separately from the candidate digest. Verification requires an existing retained manifest whose digest matches both the expected and freshly observed candidate and whose coordination ID matches the current boundary. Each digest has its own exclusively created file; earlier evidence is never overwritten. A legacy `manifest.json`, if present and valid, remains readable and is not migrated or overwritten. This detects ordinary replacement, not deliberate copying or forgery. The marker is not authenticated ownership or a security sandbox: a person deliberately disguising source as a valid artifact, or hostile concurrent filesystem mutation, is outside this guarantee. Inspect and own the boundary before use. Its exact path is recorded in the manifest as an exclusion. `all-task-relevant` means all *other inventoried paths* were included; it is not literal whole-worktree coverage and relies on the boundary containing only those coordination artifacts.

The selection format and v2/v3 candidate manifests replace the earlier v1 allowlist format; earlier manifests are not silently migrated or comparable and require a newly authorized observation.

```sh
CANDIDATE=/physical/path/to/pi-toolkit/scripts/addy-candidate.mjs
PROJECT=/absolute/path/to/project-worktree-root
TASK=my-fresh-task
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts init-coordination "$TASK"
BOUNDARY="$PROJECT/.agent-work/addy-coordination/$TASK"
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts --coordination "$TASK" inventory
# After explicit review, create "$BOUNDARY/selection.json" with {"include":[...],"exclude":[...]}.
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts --coordination "$TASK" capture "$BOUNDARY/selection.json" --write-manifest
# The retained manifest is "$BOUNDARY/manifests/<captured-digest>.json".
# Create/update the graph in "$BOUNDARY" with graph name "graph", then:
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts --coordination "$TASK" verify "$BOUNDARY/selection.json" '<captured 64-hex digest>'
```

For an authorized linked worktree, set `PROJECT` to that worktree root and add `--authorize-linked-control --linked-project-root /absolute/real/owning/project` to **each** command, including initialization. The linked worktree and its coordination boundary must be project-local within that owning root. The two authorization switches are declarations, not proof of consent. Other linked worktrees' source files are not read by this aid, but common Git storage and control metadata are in scope. Verify each worktree independently before accepting matching digests; the aid does not create or populate worktrees.

The owner can reserve exact nested linked-worktree exclusions **before** setup. Separately authorize their linked-control reads, and provide each project-relative path and expected common control-directory ID to every owner inventory, capture and verification. Paths must be under `.agent-work/linked-worktrees/`; unknown nested repositories, overlaps and invalid pointers fail closed. For example, after initializing the owner's coordination boundary:

```sh
REL=.agent-work/linked-worktrees/builder
# Pass these options on every owner inventory/capture/verify command:
OWNER_NESTED=(--authorize-nested-linked-controls --nested-linked "$REL=builder")
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts "${OWNER_NESTED[@]}" --coordination "$TASK" inventory
# Save the explicit selection, then capture --write-manifest as above, with OWNER_NESTED.
# Before setup, verify the recorded digest with OWNER_NESTED and --expect-nested-absent "$REL".
# Retain that absent-state observation as evidence.
# Only under separate worktree-creation authority, establish the linked worktree.
# Inventory again with OWNER_NESTED; retain its nestedLinkedBoundaries[].identity
# as ID in the task evidence. A missing boundary has no identity.
node "$CANDIDATE" "$PROJECT" --authorize-repository-control --authorize-coordination-artifacts "${OWNER_NESTED[@]}" --expected-nested-identity "$REL=$ID" --coordination "$TASK" verify "$BOUNDARY/selection.json" '<owner digest>'
```

Owner verification requires an explicit expected state for every declared boundary: either absent before setup, or present with the separately retained control identity. Verification returns those observed states; retain the transition in task evidence. An absent expectation is not proof that a previously present boundary was never removed: after setup, do not revert to the absent expectation without reconciliation and invalidating dependent evidence. The declaration is part of the owner manifest, whose coverage is **partial** even if no ordinary paths are excluded. Nested contents are excluded in full, not transferred or verified by the owner digest. Capture and verify each linked candidate separately; a linked mutation invalidates linked evidence even if the owner's partial digest remains unchanged. Reconcile a missing/replaced control identity and invalidate dependent evidence rather than silently adopting a new token. The graph does not enforce that linkage. These identity observations are not authenticated or an atomic filesystem snapshot.

`capture` returns a reproducible digest over HEAD, selected tree and stage-0 index metadata, SHA-256 of each selected HEAD and staged blob, and SHA-256/mode/size or missing/symlink-target records for the selected worktree paths. It reads HEAD, staged and worktree content twice, checks file identity/stat around reads, compares initial, intermediate and trailing inventories and observations, and rejects detected drift. It does not follow final symlinks; symlink parents, unsupported objects, submodules, unmerged index entries and nonzero index flags (including intent-to-add, skip-worktree and assume-unchanged) fail closed. Git diagnostics, including warnings about unreadable untracked directories even with exit status zero, also fail closed. A worktree file, HEAD blob or staged blob is limited to 16 MiB and their combined content per pass to 128 MiB. Output contains path names, hashes and symlink targets, not file bytes; retain it only where authorized. Explicitly excluded paths, Git control metadata beyond selected HEAD/tree/index information, submodule content, external resources, extended attributes/ACLs, hard-link topology, directory modes, empty directories, ownership, timestamps and the Git index stat cache are excluded. Ignored paths are not automatically excluded: they must be explicitly included or excluded. If any exclusion matters, this is not a lossless baseline for the task. The aid does not copy file contents.

If initialization fails after creating the boundary, or a manifest/graph write is interrupted, preserve the incomplete files and inspect actual state; do not blindly retry or adopt the same name. Under separate cleanup/repair authority reconcile them, or choose a fresh task name after recording the unfinished attempt. Do not delete or rewrite existing evidence without authority.

The double observation is **not an immutable snapshot or security sandbox**: transient change-and-restore, hostile control/config or parent-directory swaps, Git/object-store tampering, explicitly excluded paths, external dependencies and changes after capture can escape detection. Do not use it as proof of isolation from hostile concurrent writers. Verify again immediately before relying on an identity and after integration; any mismatch invalidates affected graph evidence. ### Comparing owner and linked candidates

Owner v4 and linked v3 manifest digests are not directly comparable. After independently capturing and retaining both manifests, their common selected state can be compared using `scripts/addy-compare.mjs`. It independently requires all six authority declarations, freshly verifies both retained candidates twice, checks the linked path and every declared nested control identity, and compares HEAD, staged blobs/modes, and worktree entries (including missing paths, modes and symlinks). It requires the same task/coordination path, every owner boundary present with its retained identity, and no ordinary excluded paths on either side; otherwise it fails closed. Each invocation compares **one** linked candidate; run it separately for each builder and retain each output, both digests and all control identities as evidence:

```sh
node "$CANDIDATE_DIR/addy-compare.mjs" "$OWNER" "$LINKED" "$TASK" "$REL" builder "$ID" "$OWNER_DIGEST" "$LINKED_DIGEST" \
  --authorize-owner-repository-control --authorize-owner-coordination-artifacts --authorize-owner-nested-linked-controls \
  --authorize-linked-repository-control --authorize-linked-coordination-artifacts --authorize-linked-control \
  --additional-owner-boundary "$REL_2=$CONTROL_ID_2=$ID_2" \
  --additional-owner-boundary "$REL_3=$CONTROL_ID_3=$ID_3"
```

Omit additional-boundary options for a single builder; for multiple builders list **all** other boundaries every time. The target's own boundary is supplied by the positional arguments and must not be repeated. An interrupted setup with an absent boundary cannot be compared as a fully established set; reconcile it first.

`CANDIDATE_DIR` is the directory containing the toolkit scripts. These flags are explicit scope declarations, not authenticated consent. A successful comparison covers only the stated manifest fields and exclusions; it is not an immutable snapshot, authentication, transfer, integration or proof of any excluded resource. A mutation or replacement requires fresh verification and comparison. The observations are sequential, not atomic.

### One-builder dirty-baseline preparation (trusted local processes only)

`scripts/addy-materialize.mjs` is a narrowly scoped one-builder preparation candidate; it copies explicitly selected content into **one fresh linked worktree**, not an integration or dispatch mechanism. It assumes trusted local processes and is not a sandbox or protection from malicious same-user parent swaps. Independently review this candidate before relying on it. The old `addy-transfer.mjs` CLI and `transferCandidate()` API remain disabled; do not rely on earlier transfer results.

Prerequisites: an authorized real owner root; a fresh coordination boundary and retained owner manifest made with the candidate CLI; one declared, currently absent `.agent-work/linked-worktrees/CONTROL_ID` target boundary and explicit declarations for every already present linked boundary; and an initialized `graph` in that boundary with the same baseline digest and a ready slice named `materialize`. The selection must include every inventoried non-prefix path, including all HEAD/index tracked paths; individual `exclude` entries are unsupported. Explicit excluded **directory prefixes** remain unobserved and are never copied. All materialization, including without prefixes, is restricted to the tested Darwin runtime with `git version 2.54.0 (Apple Git-157)`; other platforms and Git versions fail closed and have not been validated. Each source-content, repository-control, coordination read, journal write, nested/linked control, worktree creation, target-content, target-write and target-coordination grant must be explicitly declared. These switches are declarations, not authenticated consent. Ensure no worker or other local process writes the source, destination or Git controls during preparation; graph records do not enforce service or resource ownership.

For example, after the owner inventory, reviewed selection and retained capture in the preceding section, initialize the graph using that manifest digest and then invoke:

```sh
ROOT=/absolute/real/authorized/owner
TASK=fresh-task
ID=builder
DIGEST='<retained owner digest>'
BOUNDARY="$ROOT/.agent-work/addy-coordination/$TASK"
node "$CANDIDATE_DIR/addy-graph.mjs" "$ROOT" "$BOUNDARY" graph init "{\"op\":\"init\",\"baseline\":\"$DIGEST\",\"baselineRef\":\"retained owner manifest\",\"slices\":[{\"id\":\"materialize\",\"depends\":[]}]}"
node "$CANDIDATE_DIR/addy-materialize.mjs" "$ROOT" "$TASK" attempt-1 "$ID" "$DIGEST" 0 \\
  --authorize-source-content --authorize-repository-control --authorize-coordination-artifacts \\
  --authorize-journal-write --authorize-nested-controls --authorize-linked-control \\
  --authorize-worktree-create --authorize-target-content --authorize-target-write \\
  --authorize-target-coordination --accept-metadata-exclusions \\
  --authorize-excluded-prefixes --exclude-prefix '<same explicitly excluded directory>'
```

Omit the last line and the preceding continuation backslash if there are no excluded prefixes. For each already present linked worktree, add `--existing-linked CONTROL_ID=IDENTITY`; capture the owner manifest with the same prefix declarations and all nested boundaries. Each existing control identity is checked before and after target creation and in comparison. The materializer validates the selected source, writes a durable running intent, creates the absent worktree with `--no-checkout`, builds its fresh index from the selected index entries without broad checkout/add, creates selected regular files exclusively and compares retained owner/linked observations twice. It rejects selected symlinks, submodules, special modes, unsupported index flags and unsupported Git/config states. It does not overwrite existing target files or alter the source index/worktree; Git necessarily writes the explicitly authorized shared worktree-control area. It does not preserve ACLs, xattrs, hard-link topology, directory modes/empty directories, ownership, timestamps or index stat cache. `--accept-metadata-exclusions` acknowledges those limitations; do not use it if they matter to the task.

Success returns `verified-awaiting-acceptance`, the owner and linked digests, control identity, scope, evidence digest, `resultRef` and graph revision. The graph appends a `prepare` event but deliberately leaves the attempt **running** and dependent slices unready. Before dispatch or accepting the graph `finish`, reverify both candidates and compare their stated scope using `addy-compare.mjs` as above, confirm service/workspace and external-resource ownership, and explicitly decide whether to finish. Use `graph inspect` to recover the exact `prepared` values and current revision, then, only after that decision, call `graph apply` with `{"op":"finish","expected":<revision>,"attempt":"attempt-1","candidate":"<prepared.candidate>","evidence":"<prepared.evidence>","resultRef":"<prepared.resultRef as a JSON-escaped string>"}`. Mismatched prepared values are rejected. A graph finish is a declaration, not proof of ownership, consent or verification. No worker is started by this tool.

An interruption or failed write leaves the attempt unresolved and retains any partial target. Inspect the graph and actual worktree/control state; do not retry the same attempt, adopt its target or clean up automatically. Explicitly record `reconcile` as failed/abandoned after inspection, or, if a `prepare` event is visible after an uncertain fsync/response, reverify both candidates and make an explicit finish-or-reconcile decision. A partially written/corrupt journal needs separately authorized manual recovery. Neither fsync nor double observation proves power-loss durability, atomicity or absence of change-and-restore. No multi-builder integration, merge, install or live-worker validation is provided.

The earlier native-helper and macOS sandbox experiments did not establish a hostile-process boundary: selected swaps were denied under some fixture profiles, but another synthetic path escaped the deny and a restrictive global profile aborted before a normal path. Those results remain evidence of the limitation, not production isolation.

## Optional durable graph for parallel work

For a task where dependency or recovery tracking benefits from a structured record, the lead can use the toolkit's [`scripts/addy-graph.mjs`](../../../scripts/addy-graph.mjs) through its ordinary shell tool. This is an optional local coordination aid, not another execution service: it never launches a worker, creates a worktree, merges, reads candidate files, verifies hashes, authenticates approval or releases a lock. Keep using the existing service and its fixed grants. For a simple task, skip this aid. Do not put secrets or private file contents in command arguments or records.

Choose an existing project-local task workspace and a fresh graph name. The lead supplies a SHA-256 identity derived from an **authorized, complete** baseline observation and a reference to its evidence; the graph itself does not collect or copy a dirty baseline. The candidate aid above can provide its `digest` and its matching retained `manifests/<digest>.json` reference, subject to its explicit exclusions and limits. Record the matching file for each candidate, not an earlier candidate's manifest. If such an identity is unavailable, do not represent a commit ID or an incomplete manifest as a lossless baseline. The same limitation applies to every declared candidate and evidence digest. Example (replace all placeholders with actual values):

```sh
GRAPH=/physical/path/to/pi-toolkit/scripts/addy-graph.mjs
PROJECT=/absolute/path/to/project
WORKSPACE="$PROJECT/.agent-work/addy-coordination/my-fresh-task" # initialized boundary above
node "$GRAPH" "$PROJECT" "$WORKSPACE" graph init '{"op":"init","baseline":"<64 lowercase hex>","baselineRef":"authorized baseline evidence ref","slices":[{"id":"core","depends":[]},{"id":"consumer","depends":["core"]}]}'
node "$GRAPH" "$PROJECT" "$WORKSPACE" graph inspect
node "$GRAPH" "$PROJECT" "$WORKSPACE" graph apply '{"op":"start","expected":0,"slice":"core","attempt":"core-1","worker":"builder-name","workspace":"owned worktree path","taskRef":"bounded worker packet ref"}'
# Only after actual reconciliation and verification, record the actual output identities:
node "$GRAPH" "$PROJECT" "$WORKSPACE" graph apply '{"op":"finish","expected":1,"attempt":"core-1","candidate":"<64 lowercase hex>","evidence":"<64 lowercase hex>","resultRef":"reviewable evidence ref"}'
```

`inspect` returns the current `revision`, slice readiness/validity and distinct attempt workbooks. `expected` must match the latest revision; inspect and decide again after any conflict. `ready` means dependencies are recorded valid and no attempt for that slice is running, not permission or proof that shared resources are isolated. Starting a new attempt invalidates dependent evidence immediately; its new attempt identity invalidates downstream results even if its output hash matches an earlier attempt. A `baseline` operation (`op`, `expected`, `digest`, `ref`) records a new baseline observation and invalidates old evidence, including when the digest is unchanged. `finish` rejects an attempt whose recorded baseline or dependency attempts have become stale. After interruption, inspect actual service state, side effects and resources; explicitly record `reconcile` (`op`, `expected`, `attempt`, `outcome`: `failed` or `abandoned`, `note`) before a new, uniquely named attempt. A reconciliation note is a declaration, not proof of release or authority.

The append-only numbered journal uses exclusive event creation and fsync, so concurrent writers conflict rather than silently overwriting one another. New v2 entries each carry a checksum, including the tail, and are limited to 1 MiB of serialized UTF-8 bytes; `inspect` reports `checksummed-v2`. A partial, malformed or inconsistent entry blocks further use: preserve it and reconcile manually, never retry the side effect blindly. Existing v1 journals remain inspectable as `legacy-v1-unsealed-read-only`, but cannot be appended to or silently migrated. Checksums and the chain detect ordinary corruption, **not adversarial rewriting**; without an independently trusted anchor they also cannot detect removal of a valid tail. They cannot detect unobserved external mutations, prove durable storage behavior, or replace a real filesystem lock. Do not delete or rewrite records. Graph state is not a workspace snapshot and does not integrate changes. After authorized integration, record the actual integrated candidate and redo affected checks and independent review; graph readiness alone is never acceptance.

## Compact attempt workbook

Use an existing issue or a short project-local file, for example:

```text
Task / attempt / owner / role:
Purpose, acceptance, exclusions and actual authority:
Input candidate: revision, dirty/untracked content identity and evidence location:
Slice, dependencies and dependency evidence:
Workspace and exclusive ownership; shared resources and isolation:
Expected outputs, checks and retained evidence locations:
Lifecycle: planned / running / paused / terminal; run and question IDs:
Result: exact output candidate and changed paths, checks with results, findings:
Reconciliation: external mutations, remaining work, resources released or still held:
Downstream evidence invalidated and required reruns:
```

Record transitions and evidence as they happen; never infer resource release merely from a timeout, missing notification or process restart. On interruption inspect the saved service state, run identity, partial changes, explicit limits and held resources before any continuation or replacement. A workbook cannot release a service lock, restore a session, prove a snapshot is lossless or make replay safe. The service validates saved loadouts before shared admission and on reconstruction; legacy runs without a candidate token remain exclusive. If invalidation cannot be journaled, the current runtime marks peers invalid in memory and fails closed; recovered active reviews are invalidated again on reconstruction. A failed execution checkpoint or terminal ownership write likewise retains the active slot, marks the result unresolved rather than successful, and invalidates active review peers, even if the candidate is later restored. Do not treat missing durable evidence or a clean checkout after restoration as proof that an interrupted review stayed valid. If identity, ownership or side effects cannot be established, stop and resolve the uncertainty instead of dispatching another writer. Preserve the workbook and useful evidence; cleanup requires its own authority.
